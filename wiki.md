# Dot.Charts

Purpose: this is Dot.Charts's own knowledge home — owned and maintained by the Charts platform team. It describes what this platform actually is, what it stores, and how it connects to the wider Dot Ecosystem. Dot.Brain never edits this file; it only reads what we choose to publish.

> **Related:** [Dot.Brain's ingested view of this platform](https://github.com/sakhilebhayi/Dot.Brain/blob/main/platforms/dot-charts.md)

> **This wiki is architecture and product documentation only.** It describes system design, data flow, and integration surface. It does not contain, and will never contain, trading, investment, or financial advice — actual signal/strategy content lives in the product itself, gated behind the disclosures described in §7.

---

## 1. What Dot.Charts Is

Dot.Charts is the ecosystem's AI-assisted market-analysis platform: chart interpretation, technical/statistical signal generation, strategy backtesting, and a visual strategy builder across Equity, Crypto, Commodity, and Forex. Smart Money Concepts (SMC)/ICT-style institutional analysis (the "714 Method") is implemented as a real strategy, not just a vision item. The long-term product vision is described at the ecosystem level in Dot.Brain's `platforms/dot-charts.md`; this wiki describes what is actually built today and the honest gap toward that vision.

**Status: a working product, not a prototype.** Since the last review (0.1.1, 2026-08-01), the platform grew from a single hardcoded demo endpoint into three real services: a Laravel API, a Python (FastAPI) analytics/backtesting engine, and a Vite frontend with seven wired pages. Auth, backtesting (persisted, multi-strategy, multi-asset-class), a visual strategy builder, real (non-placeholder) chart analysis, a current-state options-vol signal, and a Knowledge Pack publishing + approval + inbound compliance-gate subsystem are all built and covered by tests (210 PHP + 111 Python, all passing as of this review). **Correcting a stale figure carried forward unchanged since 0.2.0:** this line said "147 PHP + 83 Python" through every version up to 0.3.5, even as the Change Log's own entries moved past 202/85 — never re-synced here specifically. Sections below are marked **(built)** or **(planned)** so the remaining gap is explicit — and built features are described with their real, honest limits, not their aspirational end-state.

Notable implementation details worth flagging honestly:
- `ChartAnalysisController::analyzeChart` now calls the analytics service for a **real** swing-structure analysis when a symbol is known (caller-supplied or OCR-detected via `tesseract`), and only falls back to the old hardcoded placeholder (still clearly labeled `is_demo: true`) when no symbol is known or the analytics call fails. This is a genuine upgrade from 0.1.1's always-placeholder behavior — but it is explicitly *not* a backtested trading signal (see the `disclaimer` field), just structure/trend detection.
- Every backtest response is run through `DisclosureFormatter`, which adds a confidence band (derived from trade count), a strategy/params attribution string, and a fixed risk disclosure — this is the first §7 compliance-posture bullet, now genuinely implemented rather than aspirational.
- The Python analytics service does real backtests: vectorbt for the vectorized strategies (MA crossover, RSI mean-reversion, breakout, Bollinger), backtrader for the 714 Method (which needs bar-by-bar state for its SMC structure/session/confidence logic). Market data comes from `yfinance` (equity/commodity/forex) and `ccxt` — specifically `ccxt.binance()`, not the multi-exchange fallback the library name might suggest — for crypto, cached in SQLite. **Correcting an over-broad claim from an earlier review:** the fail-closed behavior only applies to a symbol's *first-ever* fetch (a cold cache raises `DataFetchError` on failure, same as before, never fabricates bars) — once any data is cached, `fetch_ohlcv_cached`'s gap-fill and tail-refresh requests are deliberately best-effort: a failed live fetch is caught, the write is skipped, and whatever's already cached is served anyway (real code comment: "Failing the whole request in that case would mean *every* repeat request with the same start_date 422s forever"). That's a reasonable tradeoff, but it does mean a live outage can silently serve stale (never fabricated) bars for anything already cached — see §8's market-data SLA decision for what this means in practice.
- The strategy builder's rule engine (`analytics/strategies/custom_rules.py`) is shared between backtesting (`/backtest` with `strategy: custom`) and validation (`/validate-rule`, called synchronously when a user saves a strategy) — the same evaluator that runs a saved strategy is the one that validated it at save time.
- Knowledge Pack generation, Ed25519 signing, and an operator approval workflow are real and tested — but see §5 for what "publishing" concretely means today versus what it doesn't yet do.
- **Removed (2026-08-10): a 10-file legacy cluster** — `EnhancedMarketDataController` and 9 services (`EnhancedMarketDataService`, `MarketDataService`, `EnhancedNewsDataService`, `NewsDataService`, `StatisticalAnalysisService`, `EnhancedStatisticalAnalysisService`, `SignalBacktestingService`, `SignalErrorMetricsService`, `SignalFeedbackService`) plus their 3 test files. This was the pre-Python-analytics-service prototype the 0.1.0 wiki already described as "usable building blocks, not a connected pipeline" — `git log` showed it untouched since the repo's first two commits, before any of the ~135 commits of real feature work. Confirmed unreachable from any route (`EnhancedMarketDataController` was never registered in `routes/api.php` at all) before deleting. `StatisticalAnalysisService` in particular was mostly fabricated placeholder values (`beta = 1.0`, hardcoded `'success_rate' => '65%'`), not real logic. One prior wiki claim this corrects: 0.1.1/0.2.0 said `SignalFeedbackService` "still writes feedback to `storage/signal_feedback.json`" — that was carried forward without re-verification; the investigation that led to this removal found it had zero live callers even before deletion, so that file was never actually being written in the current app.
- **Security audit (2026-08-10), two real findings fixed:**
  - **Stored XSS.** `history.js`'s `run.symbol` (pre-existing) and `journal.js`'s `entry.title`/`entry.body`/symbol badge (introduced with the trading journal) all interpolated raw user text directly into `innerHTML` — a journal title of `<img src=x onerror="...">` would have executed on that user's own page. With the auth token in `localStorage`, readable by any injected script, this was a real vulnerability, not cosmetic. Fixed by switching every user-controlled field to `textContent` assignment on a pre-built DOM structure (static markup still goes through `innerHTML`, since none of it is user-controlled). Verified live with real payloads (`<img src=x onerror=...>`, `<script>...</script>`, `<svg onload=...>`) against the running dev server: the probe never fired, and the rendered DOM shows browser-escaped literal text (`&lt;img src=x...&gt;`), not real elements.
  - **No global API rate limit.** Every route without its own explicit `throttle:X` — `/me`, `/logout`, the full `/strategies` and `/journal-entries` CRUD surfaces — had zero rate limiting; Laravel 11/12's minimal skeleton doesn't apply one by default, unlike older versions. Fixed with `$middleware->throttleApi()` in `bootstrap/app.php` plus a `RateLimiter::for('api', ...)` backstop (60/min per IP) in `AppServiceProvider` — the existing tighter, purpose-specific limiters (`backtests`, `auth-login`, etc.) remain the binding constraint for the routes they already cover; this only closes the gap for everything else.
  - **Found, decided (2026-08-10):** the Python analytics service (`analytics/main.py`) has no authentication at all — `/backtest`, `/chart-analysis`, `/validate-rule` will answer anyone who can reach the port directly, bypassing every Laravel-layer auth and rate limit. Given the real choice — a shared-secret header (buildable and testable now, real defense-in-depth), mTLS (needs cert issuance/rotation infrastructure that doesn't exist anywhere in this repo), or network isolation alone (no code, but only as strong as deployment config, unverifiable by tests) — the owner chose **network isolation only**: this service is an internal backend-for-backend dependency with no browser-facing consumers, so it must never be bound to a public interface, in dev or in any real deployment. No code changes: the documented dev command (`uvicorn main:app --reload --port 8001`) already defaults to `127.0.0.1`-only. Documented explicitly rather than left implicit, since this mitigation depends on deployment config this codebase can't enforce or test: a warning in `README.md`'s analytics-service section, and a code comment directly above `app = FastAPI(...)` in `main.py` recording the decision and its accepted weakness. `/backtest`'s date-range cap (added the same day, see below) is unaffected by this choice — it's enforced in-process regardless of who calls the service directly.
- **Deeper audit pass (2026-08-10), on the analytics service specifically:** reviewed `custom_rules.py`'s user-rule interpreter (no `eval`/`exec`, a closed whitelist of indicator names/comparators — safe by construction) and `data/cache.py`'s SQL (fully parameterized). One real finding, fixed: `/backtest`'s `start_date`/`end_date` had no maximum span, and crypto's `_fetch_crypto` paginates the live exchange manually (1000 bars/call) rather than one request covering the whole range — an unbounded date range there meant an unbounded number of real upstream Binance calls held open on a single request, compounding directly with the still-open no-auth finding above (nothing gates how often or how wide a direct caller can ask). Fixed with a 1825-day cap enforced once in `fetch_ohlcv_cached` (fails closed before any network call, covers `/backtest`; `/chart-analysis` was never actually at risk — its window is a fixed 180 days, not user-controlled), plus a matching `BacktestController` validation rule for a fast 422 without the round trip. Verified live against the running dev server: an over-cap request rejected in 18ms, an in-cap request completed a real fetch against live Yahoo Finance data normally.
- **Four new strategies/signals (2026-08-10), one per brainstorm→spec→plan→build cycle** (specs and plans at `docs/superpowers/specs/2026-08-10-*-design.md` / `docs/superpowers/plans/2026-08-10-*.md`), derived from reviewing awesome-quant, Machine-Learning-for-Trading, and financial-models-numerical-methods for technique ideas — none of those repos installed as runtime dependencies, every technique reimplemented locally to match this codebase's existing contracts. Qlib and GS-Quant were scoped out entirely (too large, too tightly coupled to infrastructure this platform doesn't have). Each round found and fixed at least one real bug before shipping, not just added a feature:
  - **`momentum`** — trailing 12-1-month momentum filter (`lookback`/`skip`) gated by a short-window ROC confirmation. The design spec's original pseudocode required both signals to *cross* their thresholds on the same bar, which — since ROC is a much shorter window — would fire close to never on real data; corrected during implementation to gate entry on momentum's own crossover with ROC as a level check instead.
  - **`pairs_trading`** — Engle-Granger cointegration test (`statsmodels`, new dependency) as a fail-closed correctness gate (a non-cointegrated pair produces zero signals, not a spurious spread), rolling hedge ratio via the closed-form cov/var OLS slope, z-score entry/exit/stop. Trades the spread as a synthetic single instrument (disclosed explicitly as not broker-accurate two-leg execution accounting) — this needed rebasing the spread onto a positive price level before handing it to `vectorbt.Portfolio.from_signals` (a raw spread can go negative, which the engine can't sensibly price). The second symbol (`symbol_b`) travels end-to-end inside the existing freeform `params` JSON column/dict rather than a new DB column or Pydantic field. Found and fixed a real Laravel gotcha while wiring validation: a `'params.symbol_b' => '...'` dot-path rule silently made `$request->validate()` strip every *other* `params` sub-key not covered by an explicit rule, breaking the pre-existing `custom` strategy's rule-object params — fixed with a manual conditional check instead of a dot-path rule.
  - **`ml_signal`** — a `GradientBoostingClassifier` over 7 `pandas_ta`-derived features (RSI, MACD histogram, ATR%, three return windows, close-vs-SMA20%), retrained walk-forward on a trailing window with no persisted model store (every backtest request retrains from scratch — deliberately, to avoid new training infrastructure). A dedicated leakage-regression test proves shuffling bars after a walk-forward block's training cutoff never changes that block's predictions. Explainability data (model type, top-3 features by importance, retrain-block count) is threaded through the same `params`-dict side-channel pairs_trading established for `symbol_b` — zero schema changes. Found a real fixture bug while writing the endpoint smoke test: a monotonic (always-up) synthetic price series makes the target column single-class, which the module's own `nunique()==2` guard correctly (and silently) skips training for — the test fixture needed genuine up/down variation, not just an uptrend.
  - **Options vol signal** (not a `STRATEGY_REGISTRY` entry — a separate endpoint family, see below) — a current-state volatility-regime read: realized-volatility percentile rank (an explicitly-labeled proxy for true IV rank, since `yfinance` has no historical implied-vol endpoint at all) plus ATM put-call skew from `yfinance`'s live options chain, with a small local Black-Scholes module (`pricing/black_scholes.py`, verified against textbook values and put-call parity) as a fallback IV solver when `yfinance`'s own `impliedVolatility` field is `0` (a real, observed condition for stale/illiquid quotes). Found while prototyping: the nearest-*listed* expiry is often 0-1 DTE with zero open interest and implausible (>200%) "implied vols" from wide/stale quotes — switched to nearest-to-30-days instead (the standard front-month convention), which gave sane readings against the same live symbol. Scope was deliberately narrowed during brainstorming from an initial ask for full options-*position* backtesting: `yfinance` only exposes the *current* chain, never historical strikes/expiries/quotes, so there is no real data anywhere in the stack to backtest option positions against — building that would mean fabricating historical quotes, which this codebase has held the line against since 0.1.1. Exposed as `GET /options/vol-signal/{symbol}` (analytics) / `GET /api/options/vol-signal/{symbol}` (Laravel, its own `options-vol` rate limiter at 20/hour by IP, unauthenticated by design like `chart-analysis`) rather than forced into `/backtest`'s shape — there's no portfolio, entries, exits, or trades, so it's a current-state read, same category as `/chart-analysis`, not a strategy. Not persisted anywhere — stateless by design, same "don't build storage nothing needs yet" discipline as everywhere else in this codebase.

  All four verified live against real data before being called done, not just passing tests: momentum and pairs_trading against real AAPL/MSFT backtests, ml_signal against a real 4-year AAPL backtest (87 trades, 26 retrain cycles), and the vol signal against the real live options chain (real spot price, real realized-vol percentile, real skew). Full suite growth across the four: analytics 88→111 tests, backend 203→210 tests.

## 4. Events Emitted

**Real, but local-only.** Two domain events now exist and are dispatched on real triggers:
- `StrategyPerformanceCycleCompleted` — dispatched by `ObservationPackGenerator` whenever a monthly observation pack is generated (above the n≥50 floor) for a strategy class.
- `ComplianceGateRejected` — dispatched by `InboundMnpiGate` whenever an inbound pack is rejected by the content-materiality screen.

Both currently have exactly one listener each (`LogStrategyPerformanceCycle`, `LogComplianceGateRejection`), and both listeners only log — there is no queue, event bus, or webhook that carries these off this platform today. Dot.Brain's `platforms/dot-charts.md` specifies a target event set (`trading.signal.issued/expired`, `trading.compliance.gate_rejected`, `trading.strategy.performance_cycle`); the two events built here are conceptually aligned with two of those three, but naming doesn't match exactly and there is still no actual transport to Dot.Brain. Flagging this explicitly rather than implying an event bus exists because the class names sound like one.

## 5. Connecting to Dot.Brain

Dot.Charts is registered in Dot.Brain's platform registry as `dot-charts`. `platform.dkp.json` (a real manifest, not a placeholder) declares a real Ed25519 signing key, a publish/response topic pair, and a PR repository. What's built is a **generate → approve → retrieve** pipeline plus a real, tested (but honestly unverifiable end-to-end) publish client — see the sub-sections below for exactly what that means.

| Payload type (as implemented) | Target cadence | Current status |
|---|---|---|
| `metric` | monthly | **built**: `knowledge-packs:generate` runs monthly via the scheduler per known strategy class, enforces an n≥50 account-aggregation floor, and always includes worst-drawdown + negative-return-rate (the loss-honesty invariant, never omitted) |
| `insight` | per finding | **built**, manual trigger only (`dkp:generate-insight`) — not on the scheduler |
| `incident_report` | per incident | **built**, manual trigger only (`dkp:generate-incident`) — not on the scheduler |
| `recommendation` | per verified recommendation | **built**, manual trigger only (`dkp:generate-recommendation`); today there is exactly one recommendation content (the loss-honesty structural-invariant proposal), not a general recommendation-authoring flow |

**Correction from the last review:** the previous version of this wiki flagged `payload_type` naming as drifting from Brain's spec (`observation`/`insight`/`outcome`/`incident`). That was comparing against `platforms/dot-charts.md`'s informal summary table. Having now read `brain.dkp.md` (Dot.Brain's actual protocol spec) and its `knowledge-pack.schema.json` directly, the real, authoritative `payload_type` enum is `metric`/`insight`/`recommendation`/`incident_report` — exactly what's implemented here. There was never a real drift; the earlier flag compared against the wrong source.

Every generated pack starts as `pending_approval` (unsigned). An operator (`is_platform_operator`, settable only outside any request payload) must call `POST /knowledge-packs/{id}/approve` or `/reject`. Approval does two things, in order: (1) runs `OutboundMnpiGate` against the pack's own title/summary/payloads — fail-closed, same instrument-map keyword match as the inbound gate; (2) only if that passes, produces the Ed25519 signature and self-verifies it before persisting. A blocked approval — outbound-gate rejection or the "pack not pending" state conflict — returns a clean `422` with an explanatory `error` message, not a bare `500`. Approved packs are retrievable via `GET /knowledge-packs/{id}` with the full signed envelope; a separate `POST /knowledge-packs/ingest-check` runs the inbound gate against a pack-shaped payload before Dot.Charts would accept content *from* another platform.

### What "publishing" actually means today (audited 2026-08-10)

Read `~/Dot/Dot.Brain` directly before building anything further here, rather than guessing at what a "transport path" should call. Finding: **Dot.Brain has no deployed infrastructure anywhere.** It is ~40 markdown specs (architecture, protocol, governance) plus 3 small, unrelated Node CLI tools — no server, no Dockerfile, no deploy config, no resolvable hostname (the one URL example in its docs uses `.dot`, not a real TLD). Its own non-negotiable rules describe the intended architecture as Dot.Brain *pulling* Knowledge Packs and responding via **GitHub Pull Requests** to each platform's repo — not a live API Dot.Charts would poll or push to in the conventional sense. `brain.api.md` additionally documents a concrete write endpoint, `POST /v1/dkp` (the "Ingestion Gateway": `202` + receipt on success, `4xx` + a normative `DKP_*` error code otherwise), while `brain.dkp.md §8` separately describes publish/subscribe over per-tenant message topics with mutual TLS — two different transport models in Dot.Brain's own docs, not reconciled with each other.

Given that, here's what's real:

- **`DkpBrainClient`** (`app/Services/DkpBrainClient.php`) implements the `POST /v1/dkp` REST contract exactly as documented — chosen over the pub/sub model because it's the only one of the two specific enough to build against without guessing at unconfirmed broker infrastructure. It handles the documented response codes (`202` success, `429` rate-limited, `DKP_DUPLICATE` as a non-error ack, any other `4xx` as a rejection with its real error code) and the documented retry policy (exponential backoff, base 2s). It **refuses to attempt a call while `services.brain.dkp_endpoint` is unconfigured** (throws immediately, no silent no-op) rather than pointing at nothing. It is **honestly unverifiable end-to-end** — there is nothing real to test it against — so every test for it uses `Http::fake()`, proving the client's own request/response handling is correct against the spec, not that a live integration works.
- **`php artisan dkp:publish {id}`** is the only way to invoke it — manual-only, matching this app's existing convention for one-off DKP operations. Nothing calls `publish()` automatically.
- **Deliberately not implemented:** mutual TLS (brain.dkp.md §8's other stated auth mechanism). Client-certificate custody is a credential-ownership concern on the same level as the DKP signing key itself — there is no real certificate to hold yet, and this codebase has held the line all along on not fabricating credential material.
- **`DkpEnvelopeSchemaConformanceTest`** vendors Dot.Brain's real `knowledge-pack.schema.json` (`resources/dkp/`, provenance recorded in `resources/dkp/README.md`) and validates every generated payload type against it. Result: every real, approved (signed) pack this platform generates — `metric`, `insight`, `incident_report`, `recommendation` — genuinely conforms. This is the honest substitute for an end-to-end test: it proves Dot.Brain's own validation *would* accept these envelopes, without needing anything deployed to prove it against. (An unapproved, unsigned pack correctly does *not* conform — asserted directly as expected behavior, not a bug.)

Net effect: the moment a real Dot.Brain endpoint exists and gets configured, publishing is one artisan command away, sending an envelope already proven to conform to Dot.Brain's real schema. Until then, approved packs sit in this platform's own database and API.

## 6. Naming Discrepancy (resolved 2026-08-10)

Dot.Brain's registry and knowledge document refer to this platform as **`dot-charts`**, and this wiki keeps the "Dot.Charts" product name for ecosystem consistency. The GitHub repository was previously named `ChartSense`, diverging from both the registry ID and the sibling-platform convention (Dot.Mines, Dot.Brain, etc. all have repo names matching their product names). Decided: keep the `dot-charts` registry ID as-is, but rename the repo to match the product name — the repo is now `github.com/sakhilebhayi/Dot.Charts`. ## 7. Compliance Posture

Per Dot.Brain's framing, Dot.Charts is the ecosystem's only regulated-market platform. Status against the two invariants from the last review:
- **Signal disclosure — now built.** Every backtest response served by `POST /api/backtests` carries a `disclosure` object (confidence band, strategy/params attribution, fixed risk-disclosure text, max drawdown, losing-trade count) via `DisclosureFormatter`. Chart-analysis responses carry an equivalent `disclaimer` field, distinguishing real (`is_demo: false`) from placeholder results. Neither response type presents a number as real when it isn't. The 2026-08-10 strategy additions (§2) extend this rather than bypass it: `pairs_trading`'s attribution states plainly that its metrics describe a synthetic single-instrument spread, not two separately-filled legs; `ml_signal`'s states the model type, retrain cadence, and top features by importance, closing with "a prediction, not a rule"; the options-vol signal — not a backtest, so it gets its own smaller disclosure shape via `DisclosureFormatter::formatVolSignal()` rather than being forced through the backtest-shaped one — states explicitly that its realized-vol rank is a proxy for true IV rank, not IV rank itself.
- **User positions/orders — still never persisted, by design, and now with an automated guard.** No schema exists for it, across a full backtesting/journal-adjacent feature build-out (backtest runs, custom strategies, Knowledge Packs, and now the trading journal itself — the table most likely to have accumulated position/order fields if this discipline were going to slip). `JournalEntriesSchemaInvariantTest` (added with the trading journal, §3) is a real, running CI check: it inspects `journal_entries`' actual columns and fails the build if any position/order/P&L-shaped name ever appears. This closes the "not enforced by any automated schema-level guard" gap the last review flagged — that gap is specific to the journal table; the invariant is still not mechanically enforced across every other table in the schema.

**`/register` and `/login` rate limiting — now built (closed 2026-08-10).** `login` is capped at 5/min keyed by email+IP (not IP alone, so one attacker can't dodge the limit by rotating the target email, and not email alone, so a botnet can't lock a real user out of their own account); `register` is capped at 5/hour per IP. Verified against the live dev server, not just the test suite: 6 rapid real HTTP requests to a running `php artisan serve` returned five real responses then a `429` on the sixth, for both endpoints.
